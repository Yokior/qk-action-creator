# 步骤组与子程序拆分决策

## 用途

- 这份文档专门回答复杂动作里“什么时候用 `sys:group`，什么时候用 `sys:subprogram`”。
- 目标不是说明语法，而是固化结构拆分规则，避免把主流程写成一长串平铺步骤。

## 先记结论

- 只为分阶段、折叠、统一观察：
  - 优先 `sys:group`
- 同一段逻辑会复用两次及以上：
  - 优先 `sys:subprogram`
- 逻辑只有一个调用点，但内部已经很长：
  - 先 `sys:group`
  - 仍然过长再拆 `sys:subprogram`
- 主流程默认优先做编排，不承载大段实现细节。

## 决策表

### 适合 `sys:group`

- 同一阶段有多步连续操作。
- 该段逻辑只在一个地方使用。
- 只是为了把“初始化 / 读取配置 / 主执行 / 收尾”分开。
- 需要统一启停、折叠、观察。
- 需要临时调试某一整段流程。

### 适合 `sys:subprogram`

- 同一逻辑会被调用两次及以上。
- 逻辑本身有明确业务名字。
- 主流程已经不适合继续承载细节。
- 同一动作存在多个模式，共享一部分公共能力。
- 希望主流程更像调度表，而不是实现细节表。

## 主流程默认职责

- 获取输入。
- 读取状态。
- 判断入口参数。
- 决定进入哪个分支。
- 调用子程序。
- 在阶段边界给出提示或停止。

主流程默认不应承担：

- 大段列表/词典加工细节。
- 大段界面项构造细节。
- 可复用的文件处理中间逻辑。
- 一整个模式的完整实现。

## 推荐结构

### 小动作

- 主 `Steps` 直接完成。
- 仅在明显阶段处用一两个 `group`。

### 中等动作

1. `group`：初始化默认值
2. `group`：读取配置
3. `simpleIf` / `if`：判断入口
4. `subprogram`：执行主能力
5. `group`：收尾

### 大动作

1. 主流程只保留调度层
2. 每个大阶段用 `group`
3. 每个可复用能力下沉为 `subprogram`
4. 子程序内部继续按阶段使用 `group`

## 命名规则

- 步骤组名称应直接写业务阶段：
  - `初始化默认配置`
  - `读取动作状态`
  - `判断入口`
  - `生成菜单项`
  - `执行主功能`
- 子程序名称应直接写业务目的：
  - `加载配置`
  - `构造操作项`
  - `发送文本片段`
  - `执行OCR模式`

不要使用：

- `步骤组1`
- `处理逻辑`
- `子程序A`
- `测试`

## 对 qk-action-creator 的直接约束

- 需求一旦出现两个以上明显阶段，优先引入 `group`。
- 同一逻辑被两个分支复用时，优先抽成 `subprogram`。
- 不要为了“看起来高级”把所有阶段都拆成子程序。
- 不要为了“少建子程序”把所有实现细节糊在主流程。
- 复杂动作生成时，先决定结构骨架，再填模块步骤。

## 典型结构表现

- 配置管理型动作：
  - 常见“步骤组分阶段 + 子程序承载具体能力”。
- 单功能多模式动作：
  - 常见“主入口统一 + 多模式子程序分发”。
- 规则驱动型动作：
  - 常见“顶层像调度表，细节大量下沉”。
