# 列表与词典驱动动作设计

## 用途

- 这份文档专门说明什么时候应该先建 `List` / `Dict`，而不是先拼接文本。
- 目标是让 `qk-action-creator` 在生成中大型动作时，优先按容器建模，而不是按字符串堆逻辑。

## 先分清两类容器

### 列表

- 适合保存一组有顺序的值。
- 常见场景：
  - 文件路径集合
  - 批量处理项
  - 菜单项序列
  - 分词结果
  - OCR 结果列表

### 词典

- 适合保存按键访问的数据。
- 常见场景：
  - 一组配置项
  - 菜单项完整对象
  - 规则项
  - 命名参数集合
  - 表单维护的数据结构

## 什么时候优先列表

- 数据有天然顺序。
- 后续要遍历。
- 后续要筛选、切片、拼接、排序。
- 同一结构中每项字段很少，或每项就是一个文本值。

对应模块通常是：

- `sys:listOperations`
- `sys:each`
- `sys:repeat`

## 什么时候优先词典

- 数据按键名读取更自然。
- 后续要和表单、状态、配置联动。
- 每项字段语义明确，不适合只靠位置序号读取。
- 后续要从一个键快速取值或改值。

对应模块通常是：

- `sys:dictOperations`
- `sys:form`
- `sys:stateStorage`

## 决策规则

- “一组配置项”：
  - 默认词典
- “一组待遍历项目”：
  - 默认列表
- “菜单项既有顺序又有多个字段”：
  - 外层列表
  - 内层每项用词典或操作项对象
- “需要保存长期配置”：
  - 先词典，再决定是否写状态

## 成熟组合

### 配置型动作

1. 初始化配置词典
2. 读动作状态
3. 若非空则回填词典
4. 打开表单编辑词典
5. 保存词典回状态

### 规则驱动型动作

1. 先得到规则列表
2. 遍历列表
3. 每项内部按词典键读取条件
4. 命中后进入执行分支

### 菜单生成型动作

1. 先准备操作项列表
2. 每项内部组织标题、图标、数据、动作方式
3. 最后整体交给 `custompanel` 或相关界面模块

## 不要这样做

- 不要把多项结果先拼成长文本，再靠正则反复拆。
- 不要把一组配置散落成很多互不关联的顶层变量，除非这些字段本来就是动作固定变量。
- 不要把词典强行当列表下标使用。
- 不要把列表里每项的语义完全依赖“第几个位置代表什么”。

## 对 qk-action-creator 的直接约束

- 需求一旦出现“批量”“多项”“遍历”“一组配置”，先判断是否应建列表或词典。
- 不要在还没确定容器形态前，先急着写流程步骤。
- 需要持久化一组配置时，默认优先词典。
- 需要按顺序处理一组项目时，默认优先列表。
- 当 `listOperations` / `dictOperations` 已能完成需求时，不要改用脚本重做同样的容器操作。

## 典型结构表现

- 规则驱动型动作：
  - 规则与菜单项通常依赖列表、词典驱动。
- 配置管理型动作：
  - 配置和条目状态通常接近容器驱动模型。
- 多类型识别型动作：
  - 多规则、多类型分发通常依赖容器结构。
