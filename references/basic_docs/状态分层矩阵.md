# 状态分层矩阵

## 用途

- 这份文档专门说明 `SaveState`、`sys:stateStorage`、`sys:clouddata` 的分工。
- 目标是避免把所有“要记住的数据”都混成一种保存方式。

## 三层状态

### 第一层：普通变量

- 作用范围：
  - 当前一次运行
- 适合：
  - 中间结果
  - 临时输入
  - 当次流程上下文

### 第二层：`SaveState`

- 作用范围：
  - 动作变量本身的持久化
- 适合：
  - 明确就是动作变量，且希望保留其值
  - 固定结构的小量配置
- 不适合：
  - 复杂对象拆装逻辑
  - 明显需要按键分层管理的独立状态集合

### 第三层：`sys:stateStorage`

- 作用范围：
  - 本动作、本机、跨运行持久化
- 适合：
  - 配置项
  - 上次结果
  - 历史值
  - 本机缓存
- 默认优先：
  - 只要需求是“下次运行还要继续使用”

### 第四层：`sys:clouddata`

- 作用范围：
  - 跨设备、跨账号同步
- 适合：
  - 明确要求多设备共享
  - 云端同步配置或共享数据
- 不适合：
  - 普通本机配置
  - 每次运行都会快速变化的本地中间状态

## 决策矩阵

### 本次运行临时值

- 用普通变量

### 本机长期配置

- 默认 `sys:stateStorage`

### 固定动作变量并希望记忆上次值

- 可考虑 `SaveState`

### 多设备共享配置

- `sys:clouddata`

### 一组配置项

- 先词典
- 再决定写入 `stateStorage` 或 `clouddata`

## 单一结论

- 没有跨设备要求：
  - 不要先用 `clouddata`
- 只是当前运行内要传值：
  - 不要先落状态
- 要长期保存且属于本动作本机配置：
  - 默认 `stateStorage`

## 对 qk-action-creator 的直接约束

- 遇到“设置参数”“下次继续沿用”类需求，默认先考虑 `sys:stateStorage`。
- 只有用户明确要求跨设备共享，才考虑 `sys:clouddata`。
- 不要为了保存一两个简单值，先改用脚本自管文件。
- 需要维护一组配置时，优先先收束为词典，再存状态。

## 典型结论

- 只要动作同时带设置入口、主功能入口、长期配置，就应把状态管理视为骨架问题，而不是附加功能。
