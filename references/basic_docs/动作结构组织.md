# 动作结构组织

## 用途

- 用于指导复杂动作如何通过步骤组和子程序提升可读性、扩展性、解耦。
- 这不是语法文档，而是 `qk-action-creator` 的结构化生成规则。

## 对 qk-action-creator 的直接约束

- 简单动作可以直接放在主 `Steps`。
- 复杂动作不要把所有步骤平铺在主 `Steps`。
- 主 `Steps` 优先承担“编排层”职责：
  - 获取入口参数
  - 分发流程
  - 调用子程序
  - 组织大阶段
- 大块单次逻辑优先用步骤组。
- 可复用逻辑优先抽到顶层 `SubPrograms`。
- 子程序内部如果仍然很长，继续用步骤组分段。

## 何时优先用步骤组

- 同一阶段有多步连续操作。
- 需要整体折叠、整体禁用、整体观察。
- 该段逻辑只在一个地方使用。
- 想把主流程分成“预备 / 计算 / 输出 / 收尾”等清晰阶段。

## 何时优先用子程序

- 同一段逻辑会复用两次及以上。
- 逻辑本身有明确业务名称。
- 主流程已经过长，需要把细节下沉。
- 希望主流程更像“调度表”而不是“实现细节表”。

## 命名规则

- 步骤组的 `Note` 应直接写业务阶段名。
- 子程序的 `Name` 应直接写业务目的。
- 不要使用“组1”“步骤组2”“子程序A”“处理逻辑”这类空名字。
- 优先使用：
  - `预备`
  - `读取配置`
  - `获取输入`
  - `生成菜单项`
  - `更新状态`
  - `统计字数`

## 结构结论

- 复杂动作应大量使用“步骤组 + 子程序”分层组织。
- 主流程更偏编排层，细节逻辑应下沉到步骤组或子程序。
- 多个独立能力优先拆进顶层 `SubPrograms`，主流程通过 `sys:subprogram` 调用。
- 按功能拆出子程序后，主流程应更像调度表，而不是实现细节表。

## 使用判断

- 用户需求涉及多个阶段、多种功能、多个入口，先看这份文档。
- 当你已经开始担心“主流程太长不好读”时，就应该拆组或拆子程序，而不是继续平铺。
